# Architecture

## Modules

| Module | Responsibility |
| --- | --- |
| main.py | Streamlit views, filters, forms, user feedback |
| database.py | SQLite connections, additive initialization, transactional lead/task writes |
| intake.py | Shared input validation and submission fingerprints |
| followups.py | Urgency policy and UTC timestamps |
| analytics.py | Reporting calculations, New York filters, CSV exports |
| charts.py | Plotly presentation and calendar axes |
| notification_messages.py | Plain-text message templates and outbox inserts |
| notifications.py | Idempotent reminder checks, local processing, retry state |
| delivery.py | Delivery protocol and local-only adapter factory |
| config.py | Environment configuration and shared service categories |
| demo.py | Isolated fixture generation, reset, local demo launcher |
| backup.py | Verified SQLite snapshots and non-overwriting recovery |

The application uses standard-library SQLite with one connection per operation. Connections enable foreign keys, use a 10-second busy timeout, and close explicitly. Writes commit or roll back as a unit. Intake and local outbox workers acquire immediate write transactions to serialize competing operations.

## Schema

| Table | Key fields and relationships |
| --- | --- |
| leads | id; name/email/phone; service/description/urgency; status; created_at |
| followup_tasks | id; unique lead_id → leads; created_at; due_at; completed_at |
| intake_submissions | submission_key primary key; lead_id → leads; fingerprint |
| notification_outbox | id; unique event_key; lead_id → leads; task_id → followup_tasks; recipient/subject/body; status/mode; timestamps; attempts/receipt/error |
| demo_metadata | demo-only seed, snapshot time, inquiry count |

Follow-up timestamps use offset-aware UTC ISO strings. Legacy lead timestamps remain in SQLite's original naive UTC format. Initialization is idempotent and additive; it does not rewrite historical records or infer historical events.

## Intake transaction

1. Validate and normalize the form fields.
2. Look up the optional persistent submission key under a write lock.
3. Return the existing inquiry for the same key/payload; reject a key reused with different content.
4. Insert the lead, its task, customer/owner messages, and submission-key mapping.
5. Commit together, or roll back together on failure.

The UI retains its key for an unchanged form during a session. Editing the form starts another submission. This is retry protection, not cross-session customer deduplication; separate sessions can intentionally submit similar requests.

## Outbox lifecycle

Pending → Previewed for successful local processing, or Failed on adapter failure. Failed → Pending requires a manual retry. Unprocessed reminders can become Cancelled when a task is completed, rescheduled, or no longer satisfies the reminder condition. Previewed history is retained. Sent and sent_at are reserved; this release never uses them.

Upcoming and overdue events have independent unique keys containing the task ID and deadline. Repeated scheduler checks, concurrent workers, and Streamlit reruns do not add the same event twice. No retroactive customer confirmations are generated by migration. Message bodies are immutable event snapshots, so later lead edits do not rewrite their history.

The local adapter returns a receipt without external I/O. Processing occurs inside a SQLite transaction, which is suitable for this short local operation. A future network adapter needs a durable claim/lease, timeout handling, provider-side idempotency, retry/backoff policy, approved owner routing and credentials, and recovery for a crash after provider acceptance but before database commit. Do not substitute network delivery into the current transaction and claim exactly-once email delivery.

## Operational limits

All records are currently loaded into memory for local reporting. Large datasets need pagination and database-side aggregation. SQLite write locking limits concurrent workloads. Status transition history is not stored; analytics report current state. The notification CLI is scheduler-compatible but is not an always-running worker.
